# Technical Discussion Notes: No-Code Application Builder Integration


## 1. Project Context and Environment

The team is working with a no-code application builder that builds applications within Banks internal infrastructure.

**Current environment:**
- Multiple Linux-based application instances.
- Shared NAAS infrastructure across multiple instances: multiple VMs share the same volume, which holds the code builder, the generated applications, and environment variable storage. Ports may differ per VM based on that system's availability.
- Authentication and authorization managed through PBAC roles (`pbroles`).
- Server login and access are managed through `pbroles`, service ID, and UNIX groups, scoped to an AIT (the builder platform's application ID).
- Different projects may use different AITs (as discussed on the call), so access, service IDs, and UNIX groups may vary per project.
- Automating deployment of the generated projects within the deployed server is in MVP 1 scope (see 2.9).


## 2. Initial Scope: Technical Workstreams

### 2.1 Dynamic Port Allocation and Application Hosting
- Implement dynamic port allocation for applications published through the builder.
- Identify and manage available ports across multiple Linux-based instances.
- Avoid port conflicts when multiple applications are published simultaneously.
- Support multiple published applications running on different host ports.
- Define how application-to-port mappings will be maintained and managed.

### 2.2 Dynamic Configuration and Environment Variables
- Determine how configuration variables can be injected dynamically at runtime.
- Support environment-specific configurations without modifying generated application code.
- Explore secure management of configuration values across multiple instances.
- Validate how the approach works for frontend and backend applications.

### 2.3 UI-to-Backend Connectivity
- Establish connectivity between UIs generated by the no-code builder and backend applications.
- Support backend services hosted on different instances or ports.
- Define how backend endpoints and service URLs will be configured dynamically.
- Validate connectivity for different application frameworks and deployment patterns.

### 2.4 CORS Management
- Investigate server-side approaches to managing Cross-Origin Resource Sharing (CORS).
- The no-code builder is not expected to manage CORS configurations directly.
- Evaluate centralized or backend-level CORS configuration to allow authorized frontend applications to communicate with backend services.
- Validate allowed origins, HTTP methods, headers, and credential handling as applicable.

### 2.5 Authenticated Hosts and Access Control
- Identify how authenticated hosts are configured and accessed within the environment.
- Validate compatibility with the existing PBAC role-based access model.
- Clarify how server login and access work through `pbroles`, service ID, and UNIX groups for an AIT.
- Account for different projects using different AITs, including how access is separated and managed per AIT.
- Determine how access to published applications and backend services will be controlled.
- Document dependencies on the bank’s internal authentication and authorization mechanisms.

### 2.6 Autoscaling
- Explore autoscaling for published applications running on Linux-based instances.
- Define the conditions and metrics that could trigger scale-up.
- Investigate how dynamically allocated ports, application routing, and instance registration will behave as capacity increases.
- Assess the implications of shared NAAS infrastructure.

### 2.7 Application Versioning and Dependency Resolution
- Establish an approach for managing application versions and package dependencies.
- Investigate dependency resolution when multiple applications require different versions of the same package.
- Ensure dependency updates do not unintentionally alter or break generated application code.
- Evaluate compatibility, reproducibility, and rollback options.
- Test version availability and installation behavior across supported frameworks.

### 2.8 NPM Package Installation and Private Artifact Registry
- Explore setting up a private JFrog Artifactory repository as the package registry instead of relying directly on the public NPM registry.
- Configure npm and pip clients to use the private Artifactory remote and virtual repositories.
- Investigate package caching, approved package versions, and dependency availability.
- Explore how vulnerable or disallowed package versions can be removed from the available package catalog in accordance with the bank’s security policies.
- Validate dependency resolution when requested package versions are unavailable, restricted, or vulnerable.
- Ensure that generated application code remains unchanged wherever possible, with dependency management handled through the build and installation process.

**Important consideration:** Removing or blocking vulnerable packages must be tested against existing dependency trees to understand compatibility impacts. Lockfiles, transitive dependencies, and reproducible builds should be considered as part of the validation.

### 2.9 Automated Deployment of Generated Projects (MVP 1 Scope)
- Figure out a way to automate deployments of the generated projects within the deployed server.
- Ensure deployment runs under the correct `pbroles`, service ID, and UNIX group for the AIT that owns the project.
- Support projects owned by different AITs without cross-project access conflicts, so deployment is not tied to a single AIT.
- Integrate with dynamic port allocation (2.1), dynamic configuration (2.2), and dependency installation via the private registry (2.8), so deployments need no manual steps or changes to generated code.
- Define how deployments are triggered, tracked, and rolled back.


### 2.10 Published Application URL Resolution
**Problem:** The builder runs on a scalable set of VMs, so a user's session can land on any instance. After a build, the user needs a URL that reaches the published application regardless of which VM built or hosts it. Everything must stay within the allowed environment (shared volume, VMs, private Artifactory).

**Shared vs per-VM (see `bofa-concept.drawio`):**
- Shared on every VM through the common volume: code builder, applications, environment variables namespace.
- Per VM: the available ports. The port registry must therefore be keyed by VM.

**Proposed process:**
1. The user clicks Publish and the request lands on any builder VM.
2. The generated project is written to the shared volume under `apps/<ait>/<appId>/releases/<n>/`.
3. Dependencies are installed through Artifactory and the app is built with `BASE_PATH=/apps/<appId>` set at build time, so generated code is unchanged.
4. A free port is chosen on the VM by binding to it, and the app starts under the AIT's service ID and UNIX group. A health check must pass.
5. A registry entry `registry/<appId>.json` is written to the shared volume with `{vm, ip, port, release, status, ait}`. Writes are atomic (temp file plus rename), and each VM writes only its own entries.
6. The user receives `https://<builder-host>/apps/<appId>/`.

**Routing:**
- Every VM runs the same Node proxy from the shared volume. It reads the registry and forwards `/apps/<appId>/*` to `ip:port`, so the user can reach any VM.
- Frontends call backends through the same path (`/apps/<backendId>/api`), which resolves backend URLs dynamically (2.3) and avoids CORS (2.4) because everything is one origin.
- A reconciler on each VM restarts apps whose VM no longer exists on a healthy VM and updates the registry. The URL stays unchanged. This supports autoscaling (2.6).

**Open questions:**
- Do user browsers reach VMs only through a single entry point (bank LB or gateway), or can they reach any VM IP and port?
- Is path-based routing (`/apps/<appId>`) acceptable, or are per-app hostnames required (needs wildcard DNS)?
- Can the process start on the receiving VM directly, or does the deploy need remote execution on another VM?

## 3. Frameworks and Technology Coverage

The PoCs should validate the proposed solutions across the following technologies:

| Technology | Areas to validate |
|---|---|
| React | Frontend configuration, backend connectivity, package installation and dependency resolution |
| Next.js | Build and runtime configuration, routing, deployment and dependency compatibility |
| Node.js / Express | Backend hosting, dynamic ports, CORS and service connectivity |
| FastAPI | Python dependency management, backend hosting, CORS and UI integration |

The package registry PoC should primarily validate NPM-based dependencies for React, Next.js, and Node.js/Express. FastAPI should be evaluated separately using a Python repository hosted in Artifactory, with a Python-specific dependency-management workflow.
